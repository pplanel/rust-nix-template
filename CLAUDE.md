# rust-boilerplate

A starter Cargo workspace (Rust edition 2024) for new services. **`CONVENTIONS.md`
is the authoritative spec** for how code here is structured, named, tested, and
reviewed. Read it before writing or changing code; this file only orients you and
records what's actually present.

## Current layout

```text
crates/
├── common/             # shared primitives (typed IDs, value types); no I/O, no runtime
├── domain/             # business logic + repository traits; no HTTP/DB; depends on common
├── server/             # axum HTTP layer + binary entry point; depends on domain
└── my-workspace-hack/  # generated by cargo-hakari; DO NOT edit by hand or delete
```

Dependencies point downward only: `common → domain → server`. Never introduce a
dependency that points upward or creates a cycle (CONVENTIONS §2).

The convention's full target shape also names `api_models`, `storage`, and
`test_support` crates — add them when a real boundary appears, not before
(CONVENTIONS §1). The boilerplate starts minimal on purpose.

`my-workspace-hack` is a workspace-hack crate managed by `cargo-hakari`: it unifies
feature flags across the workspace so deps build once. Every member depends on it
(`my-workspace-hack.workspace = true`). It is an intentional one-file crate — the
"premature splitting" rule (CONVENTIONS §1) does not apply. Never hand-edit its
`Cargo.toml` (the `HAKARI SECTION`) or remove the dependency line from a crate.

## Build environment

The toolchain and dev tools come from the Nix flake, loaded automatically by
`direnv` (`.envrc` → `use flake`). Inside the shell you get the pinned Rust
toolchain plus `cargo-nextest`, `cargo-hakari`, `cargo-release`, `cargo-edit`,
`cargo-watch`, `git-cliff`, `cocogitto`, `just`. The flake uses **crane**; builds
are named via `[workspace.metadata.crane] name` in the root `Cargo.toml`.

A root `Justfile` wraps the common workflows (`just` lists them), separating the
fast inner loop from hermetic verification:

- `just check` — fast local gate: fmt-check, clippy, nextest, hakari-verify (no Nix sandbox).
- `just check-nix` / `just build-nix` — `nix flake check` / `nix build`, hermetic, what CI mirrors.
- `just bootstrap` — re-wire the workspace-hack after adding a crate or dependency.
- `just watch` — clippy + tests on every change.
- `just release` / `release-dry` / `changelog` — cocogitto + git-cliff (need `cog.toml`/`cliff.toml`, not shipped yet).

`nix flake check` runs the whole gate (clippy, fmt, nextest, and the `server`
build) hermetically — this is what CI should mirror.

## Commands

The CI gate that must pass before merge (CONVENTIONS §15, enforced by the flake
checks):

```bash
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --workspace --all-features   # or: cargo nextest run --workspace
cargo hakari generate --diff && cargo hakari verify   # workspace-hack is current
```

Run it; all are currently green. Formatting is default rustfmt (4 spaces, 100
cols); `rustfmt.toml` exists but is empty (defaults only, no nightly options).
Lints live in the root `Cargo.toml` `[workspace.lints]` and are inherited per
crate with `[lints] workspace = true`. Clippy here runs `all` + `pedantic` +
`nursery` at warn (stricter than a stock setup), with `module_name_repetitions`
allowed; treat every clippy warning as a failure.

**When you add or change a dependency**, after editing `[workspace.dependencies]`
run `cargo hakari generate` (and `cargo hakari manage-deps` if adding a new
member crate), or `cargo hakari verify` will fail.

## What agents must keep in mind

- **Pick the right crate first** — never put logic in a layer that would force an
  upward dependency.
- **Typed errors with `thiserror`** in libraries; `anyhow` only in binaries/tests.
  No `unwrap`/`expect`/`panic!` in non-test code; no `String` errors; don't swallow
  errors (CONVENTIONS §6).
- **New dependencies** go in `[workspace.dependencies]` once, used as
  `dep = { workspace = true }`, each needs a clear reason (CONVENTIONS §14), and
  you must re-run `cargo hakari generate` afterwards.
- **Tests come with every change**; a bug-fix test must fail without the fix.
  Unit tests inline in `#[cfg(test)] mod tests`, integration tests in
  `crates/<name>/tests/` (CONVENTIONS §13).
- `unsafe_code = "forbid"` workspace-wide (CONVENTIONS §12).
- Use `foo.rs` + `foo/`, never `mod.rs`. `lib.rs` declares modules and re-exports
  the public API (CONVENTIONS §3).
- Smallest useful change, no speculative abstractions or unrelated churn, verify
  the CI gate before finishing (CONVENTIONS §16).
